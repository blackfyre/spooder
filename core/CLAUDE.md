# core/

Hardware-free C++ shared by both firmwares, the virtual robot and the host tests (`mise run test`). It includes only `<math.h>`/`<stdint.h>` (plus `<stdio.h>` for `snprintf` in `status/status_screen` and `robot/robot_tick`). The bridge compiles it under ESP-IDF, where POSIX `link()` and C++20 `std::lerp` are visible: hence `interpolate` in `movement/vectors.h`.

A change here reaches the robot, the bridge and the virtual robot: run `mise run build` (with and without `--serial`), `mise run build-bridge` and `mise run e2e` besides `mise run test` and `mise run lint` (formatting, and clang-tidy with `.clang-tidy`: fix a finding, or suppress it with `NOLINTNEXTLINE(check)` and a reason; never cast a narrowing away without the value's bound beside it).

- `movement/` (reference: the `spooder-leg-kinematics` skill):
  - `body`: the non-blocking state machine (Initialise, Stand, Walk, Sleep, Calibrate, Perform) on a fixed 5 ms internal grid.
  - `gesture`: the gestures Perform plays (say hi and wiggle so far): keyframe scripts of body shifts and lifted feet, and the player (eased, rate-limited segments; a stopped gesture finishes its keyframe, puts its feet down, then straightens).
  - `gait`, `kinematics` (IK, target validation, `servoOutputIndex`) and `vectors`.
  - `joint_calibration`: the per-joint calibration table (offset, 0° and 180° pulses, direction), its clamps, the 60°/s rate-limited `step` and `toPulse`.
  - `calibration_defaults.cpp`: the compiled defaults, in a fixed format that a front-end's export replaces whole. Its values are free to change; host tests check that it parses, stays within the guards and round-trips through the exporters.
  - `movement_command.h`: the request a controller hands to movement.
  - `body_geometry.h`: each leg's coxa pivot in the body frame, measured from upstream's frame STLs; the mount angles are gait's. The desktop's `legview` copy is pinned by `test/golden/body_geometry.txt`.
  - `centre_of_gravity`: the estimated centre of gravity (point masses for the body, the battery and the legs' servos and links; the servo and battery weighed, the rest estimates, in one table) and the support margin of the feet on the ground. Host tests only (the gesture test checks it); the desktop's `legview` has a copy.
  - `servo_profile.h`: the servo models (rated speed, share usable under load) and the build's choice, `SPOODER_SERVO_PROFILE` (default `MG996R`), which sets the joint speed budget. `body` slows its motion clock, in 20 ms pieces, to keep every joint within the budget; `robot_tick`'s output rate backstop never exceeds the rated speed.
- `protection/`: power protection and the emergency stop. It turns supply readings into "output allowed" and "force Sleep", with latched faults; `supervisor` decides when the body runs, stops or restarts.
- `protocol/`: the link's frames (version 3: command with the gesture request, telemetry with the gesture playing, calibration set and report, and the pose and diagnostics, sent on every link: the bridge relays them in WiFi drive and otherwise ignores them), CRC and incremental decoder (both firmwares; `Decoder::frameBytes()` hands out a copy of the raw bytes of the frame `next()` last returned, which the bridge relays in WiFi drive without re-encoding), pinned by `test/golden/protocol_v3.txt`. `link_receiver` is the robot's handling of decoded frames: arrival stamping, clear, mode-request and gesture-request counters, baselines after a link gap, the calibration guards and reports, and the arbitration between the bridge and USB links. A protocol change bumps `protocol::VERSION`, the Go copy in `desktop/internal/protocol` and the golden file, and both boards are flashed together.
- `robot/robot_tick`: the robot's 20 ms control tick, shared by the firmware and the virtual robot: link decoding and arbitration (or the serial keys) → protection → supervisor → calibration sets → calibration step → `body::step` → servo output → LEDs → telemetry every fifth tick, the pose frame two ticks later and the diagnostics frame (motion share, backstop, tick time, limits) four ticks later, and calibration reports, all on both links → the status line. It logs the build banner on its first tick and whenever `Inputs::usbConnected` turns true. It drives the hardware through its `Hardware` interface.
- `identity/build_identity`: the build identity's text, always printable ASCII: the console banner (`spooder <component>: build <id>`, `unknown` for an empty id, non-printable bytes as `?`, cut at 40 characters) and `fit` for the bridge screen (`..` and the id's end). `build_identity::ID` is declared here but defined only by the source `cmake/build_identity.cmake` generates in each firmware build; the host tests do not link it.
- `gamepad_mapping/`: gamepad input to the desired command state (bridge); `rumble`, the bridge's rumble feedback (fault, e-stop, link, refused gesture).
- `status/led_pattern`: what the robot's six status LEDs show; `status/status_screen`: the bridge screen's content (the drive, power and link pages with the status strip, in Bluetooth drive and WiFi drive, and the setup-mode text), with `status/power_history` (60 s of voltage and current), `status/page_button` (the left button as the page switch) and `status/peak_hold`.
- `setup/`: the bridge's setup mode. `portal_controller` (portal polls and buttons as the controller), `calibration_sync` (pending edits, one set in flight, confirmation by report), `calibration_export` (a reported table as `calibration_defaults.cpp`), `setup_entry` (the button hold and the boot decision) and `access_point` (the setup and WiFi drive network names from one MAC, password, QR text).
- `wifi_drive/`: the bridge's WiFi drive. `drive_mode` (the boot decision from the setup request and the GPIO32 switch, setup winning; the switch notice, debounced 100 ms against the running mode), `handheld_controller` (the handheld's UDP datagrams as the controller: the 8-per-20 ms window budget, validation of exactly one version 3 command frame, the sender lock, the sequence rule with jumps ending the session, the 150 ms liveness, counter translation with Sleep until a session's first mode request, the e-stop flag kept through a lapse, the relay target and the outcome counts) and `relay_queue` (a ring of 8 raw robot frames that never waits, dropping and counting when full, cleared when the session changes, and, after a session change, dropping frames until a receive poll ends with the decoder empty).

A new `.cpp` here is listed by hand wherever it is built: the root `platformio.ini`'s `build_src_filter` (host tests, and the sources clang-tidy analyses; one `+<file>` entry per source, no globs: `mise run test` fails naming a file missing there, and `mise run lint` fails too), and as needed `firmware/servo2040/CMakeLists.txt`, `tools/virtual-robot/CMakeLists.txt` and `firmware/bridge/main/CMakeLists.txt`.
