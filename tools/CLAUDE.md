# tools/

- `virtual-robot/`: the virtual robot, a native C++17 program (CMake, Ninja; `mise run virtual-robot`) running `core/robot/robot_tick` behind a pseudo-terminal that acts as the robot's USB port (frames and debug text as on the board), optionally a second one for the bridge link, or a simulated bridge. Simulated supply and servo current (`core/robot/bench_model`, shared with the robot's bench simulation; the virtual robot itself never enters simulation and reports `TELEMETRY_SIMULATED` clear); commands on standard input (`supply V`, `current A|auto`, `load K`, `bridge off|idle|gamepad|clear`, `estop on|off`, `unplug`, `plug`, `step N`, `status`, `quit`); `--help` lists the options (`--link`, `--speed`, `--stepped`, `--bridge-pty`, `--wifi-bridge`). It builds the robot's build identity source too, so its USB terminal shows `spooder robot: build <id>` on the first tick and on each tick that sees a client on its USB terminal after one that saw none (`board.usb.connected()` as `Inputs::usbConnected`). The desktop calibrator connects with `--port build/virtual-robot/usb`; `mise run desktop-sim` runs both. `--wifi-bridge [ADDR:]PORT` (`wifi_bridge.cpp`; no value: 127.0.0.1:52040, `ADDR:` defaults to 127.0.0.1, port 0 takes a free port) runs a virtual bridge in WiFi drive in place of the bridge terminal and the simulated bridge: it compiles the bridge's own `core/wifi_drive/handheld_controller` and `relay_queue` and `core/gamepad_mapping`, reads at most 32 datagrams a tick from a non-blocking UDP socket with the kernel's minimum receive buffer (so none is taken in a later tick than it arrived in, and a flood cannot hold the tick), feeds one command frame a tick into the bridge link's decoder, and sends the robot's bridge-link frames back to the locked handheld, one per datagram. It prints `wifi-bridge ADDR:PORT` before `ready`, then `session start t=<ms> from <addr>:<port>` and `session end t=<ms> accepted=<n> budget-max=<n> longest-tick-ms=<ms>`. `estop` is the bridge's GPIO35 button, ORed with the handheld's flag; the `bridge` commands are refused. It runs in real time only, so it refuses `--bridge-pty` (and `--bridge-link`), `--stepped` and `--speed`. The handheld's e2e (`desktop/handheld/e2e`, in `mise run e2e`) drives it; on the desktop, `build/handheld/amd64/spooder-handheld --addr 127.0.0.1:52040` does.
- `bridge-screenshots/`: renders the bridge screen's pages in chosen states to PNGs with the bridge's own `screen_draw` and `core/status` code on the host (LovyanGFX's Linux back end, no panel); `mise run bridge-screenshots` writes `docs/images/bridge-*.png`.
- `worktree.sh`: delivery worktrees (`mise run worktree-add <name> [base]`, `worktree-remove <name>`): `.claude/worktrees/<name>` on branch `deliver/<name>`, from `origin/main` by default, with the submodules cloned from the primary checkout (which must have run `mise run setup`) and `.pio-core` shared by a symlink. `mise run worktree-init`, run inside a worktree another tool created (Orca's setup command), does the same preparation there; it is safe to repeat.
- `vulncheck.sh` (`mise run vulncheck`): govulncheck (pinned) of `desktop/` against `desktop/vulncheck-baseline.txt`. It fails on a called vulnerability the baseline does not list, and on a listed one no longer found: the baseline only shrinks.
- `lint.sh` (`mise run lint`): the C++ static checks. It modifies no source file; it only rewrites the git-ignored root `compile_commands.json`. It lists Spooder's own C++ (tracked and untracked but not ignored, in `core/`, `firmware/servo2040/src/`, `firmware/bridge/main/`, `test/`, `tools/virtual-robot/`, `tools/bridge-screenshots/`), runs `clang-format --dry-run --Werror` on it (exclusions in `.clang-format-ignore`), then writes the host compile database (`pio run -e native -t compiledb`), checks it lists every source in the `native` env's `build_src_filter`, and runs clang-tidy (`.clang-tidy`) on its `core/` sources. It fails if either fails, a configuration is missing, or a clang tool is not the version `mise.toml` pins.
- `risk-tier.sh <base> [head]` (or `-` with paths on standard input): a change's risk tier from the paths it touches (`REVIEW.md`). A new sensitive path belongs in its high list.
