# Design

## Context

- **Link protocol** (`add-live-joint-calibration`, design D3/D4): version 2, frame types 1–4, `MAX_FRAME_SIZE` 135, golden vectors in `test/golden/protocol_v2.txt` generated by `test/test_protocol_golden` and read by the Go tests. USB frames are written whole or dropped (`usb_link::writeFrame`); the USB transmit buffer is 256 bytes.
- **Robot values already computed each tick:** `BodyState::angles` (IK result plus the applied offsets, i.e. what `joint_calibration::toPulse` receives), `BodyState::offsets` (the applied offsets the IK added), and `servo_output`'s last pulse per output (0 until the body has set the leg).
- **Desktop** (`add-desktop-calibrator`): `session` owns the state, `ui` draws snapshots in the Blackfyre look, and `ui`'s screenshot test renders states off screen.
- **Kinematics** (`spooder-leg-kinematics` skill): leg frame with the origin at the coxa pivot, x outward, z up; links 41/116/183 mm.

## Goals / Non-Goals

**Goals:**
- The drawing shows what the robot commands, from values the robot sends, not from a desktop re-run of the body.
- Byte-exact agreement of the C++ and Go pose frame, pinned by golden vectors; forward kinematics on the desktop pinned against the C++ IK.

**Non-Goals:**
- Showing the measured (physical) leg: there is no position feedback.
- A to-scale body: the body outline and coxa pivot positions are schematic.
- Changing the bridge or the UART1 link.

## Decisions

### D1. Frame type 5, pose (robot → host), 110-byte payload

```
0        flags u8: bit 0 servo output on
1        reserved, 0
2 + 6j   joint j = 0..17 in servo output order (kinematics::servoOutputIndex):
           +0 commanded angle, centidegrees i16 (IK result before calibration)
           +2 servo angle, centidegrees i16 (commanded + applied offset, before toPulse's 0–180° clamp)
           +4 pulse µs u16 (last pulse set for the output; 0 = never set since power-up)
```

- Frame size 117, below `MAX_FRAME_SIZE` (135), which stays; no buffer grows.
- Angles are rounded to the nearest centidegree and saturated to the i16 range.
- **Foot targets are not sent.** With them (36 bytes) the frame would exceed 135 and grow every decoder buffer, including the bridge's. They follow exactly from the commanded angles by forward kinematics (D5), which the golden IK vectors pin.
- **Why both angles:** the commanded angle draws the geometry (what the body intends; a wrong offset shows as a physical leg that differs from the drawing). The servo angle is what the 0°/180° limits apply to, and it uses the *applied* offsets, which may lag the reported (requested) table while a change is rate-limited, so the desktop cannot derive it reliably.

### D2. No protocol version bump

The frame is additive: a new type, sent only on USB.
- Every receiver that does not know a type rejects the frame as discarded, so nothing misreads it. The bridge never receives it.
- A bump would make the robot reject the bridge's version-2 frames until the bridge is reflashed, for a change that does not concern the bridge.
- Both C++ and Go decoders learn type 5 in this change. The C++ decoder in the robot and bridge accepts a pose frame as valid and ignores it.
- **Trade-off:** a calibrator built before this change would count pose frames as discarded and show their bytes as stray text in its log. The calibrator and firmware come from the same checkout, so this is accepted rather than versioned.

### D3. Rate and transmit budget

- Every fifth 20 ms tick (10 Hz), two ticks after telemetry, so telemetry (39 bytes) and pose (117) never share one tick's 256-byte USB transmit buffer; a calibration report (135) still fits next to either. A frame that does not fit is dropped whole, as for every USB frame.
- Sent whether or not the body runs; the outputs-on flag tells the host whether the pulses are being produced.
- Not in `--serial` builds (no USB link there).

### D4. Robot side

- `link_receiver::makePose(body, pulses, outputsOn)` (hardware-free, host-tested) builds the frame: commanded = `angles − offsets` per leg, servo = `angles`, pulses from `servo_output::pulses()`.
- `usb_link::sendPose` writes it whole or drops it. `link.cpp` (UART1) has no pose sender.
- `main.cpp` gains one call after the telemetry block. The main-loop extraction into `core/` can move it unchanged into the tick.

### D5. Forward kinematics and conventions (`desktop/internal/legview`)

From `kinematics::solveLeg` (angles in degrees, before offsets):
- coxa θ1 = atan2(y, x): the leg's vertical plane is at θ1 from the leg's x axis, towards +y;
- in that plane (r outward, z up): coxa end (41, 0); femur θ2 is its elevation above horizontal, knee = coxa end + 116 (cos θ2, sin θ2);
- tibia θ3 = 180° − the interior knee angle, so the tibia's elevation is θ2 − θ3, foot = knee + 183 (cos(θ2 − θ3), sin(θ2 − θ3));
- foot (x, y, z) = (r cos θ1, r sin θ1, z).

Checks: the calibration pose target (224, 0, 116) solves to 0°/90°/90° — femur straight up, tibia horizontal outward, foot 116 mm above the pivot; standing (190, 0, −145) has the femur about 17° up and the tibia steeply down.

**Golden IK vectors:** `test/test_leg_pose_golden` solves a fixed set of reachable targets (initialise, calibration, rest, stand, walking points of the corner and middle legs, a near-limit target) with zero offsets and writes `test/golden/leg_pose.txt` (`<name> x y z coxa femur tibia`, 4 decimals), regenerated with `SPOODER_WRITE_GOLDEN=1` like the protocol file. The Go test runs forward kinematics on each line's angles and requires the target within 0.05 mm, and the calibration line to read 0/90/90.

### D6. Top view: leg mounting

Derived from `gait.cpp` (`STRIDE_MULTIPLIER`, `ROTATION_MULTIPLIER`, `LEG_PLACEMENT_ANGLE` 56°) and the command convention (translate +y forward, +x right):
- legs 0–2 are on the left, 3–5 on the right; each leg frame is mirrored relative to the body (left: x outward, y forward; right: x outward, y backward), so in the body seen from above a positive coxa angle turns the leg clockwise;
- leg x axes in the body frame (counter-clockwise from the body's right, forward up): leg 0 124° (front left), 1 180°, 2 236° (rear left), 3 −56° (rear right), 4 0°, 5 56° (front right).
- Coxa pivots are schematic (middle legs at ±90 mm, corners at (±70, ±120) mm); the legs are drawn to scale from them.

The skill already asks to confirm which end is the front on the robot; the view labels legs by number and marks the assumed front, so a mismatch is visible rather than hidden.

### D7. The legs pane

- A fourth tab, "legs", in the right-hand column next to the log, frames and export. The selected leg is the editor's: `selection.joint / 3`, and its joint `selection.joint % 3` is drawn in the accent. Legs are numbered 1–6 as in the editor (robot index + 1).
- **Side view** of the selected leg, taking the pane's free height: pivot, coxa, femur, tibia and foot on a 50 mm grid, z up, outward to the right, the body to the left of the pivot. Each joint carries a tag with its pulse, placed away from its segments and clear of the other tags; a small top-view inset shows the coxa angle in the leg frame.
- Below it, side by side: the **joint list** (commanded angle, servo angle, pulse, limit) and a square **top view** of all six legs on the body outline, the selected leg in the accent.
- **Limits:** a joint whose servo angle is outside 0–180° is "at limit" (toPulse clamps it); within 5° of either end it is "near limit". Both are marked (yellow ring, label) on the drawing and in the list of joint values.
- A leg whose three pulses are 0 has never been set: drawn as "not set", not as geometry.
- **Staleness:** the session keeps the latest pose and its arrival time; when the pose is older than 1 s (the telemetry rule), or none has arrived on this connection, the pane shows "no pose" and no geometry. A new connection forgets the pose.
- The geometry (points, projections, limits, staleness) lives in `legview` and `session`, tested without a window; `ui` only maps points to pixels and draws.

## Risks / Trade-offs

- [Leg mounting derived from the gait code is mirrored or rotated on the real robot] → The view states its assumption (front marked, leg numbers), and the side view, which carries the calibration information, does not depend on it.
- [USB transmit budget] → D3 keeps pose and telemetry on different ticks; a dropped frame only delays the drawing by 100 ms.
- [An older calibrator shows pose bytes as stray text] → Same-checkout tools; noted in D2.
- [The commanded angle differs from the IK by float rounding of `angles − offsets`] → Far below the centidegree resolution of the frame.

## Migration Plan

1. Protocol, golden vectors and `makePose`, host-tested; the Go protocol against the same vectors.
2. Robot: `sendPose`, `servo_output::pulses()` and the call in `main.cpp`; both firmware variants and the bridge build.
3. Desktop: `legview`, the session's pose, the legs pane and its screenshots.
4. **Rollback:** revert the change; the robot then sends no pose and the calibrator has no legs pane. The protocol version is unchanged either way.
