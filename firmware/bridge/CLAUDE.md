# firmware/bridge/

The gamepad bridge: the ESP-IDF PlatformIO project for the TTGO T-Display (`mise run build-bridge`, `upload-bridge`, `monitor-bridge`). It builds with the pioarduino platform's own PlatformIO core in the git-ignored `.pio-core/` at the repository root (mise's PlatformIO only bootstraps it; the two cores pin different SCons versions). The first `build-bridge` downloads ESP-IDF and the Xtensa toolchain.

- `main/main.c`: `app_main`, which picks one of three boot paths once, before either radio starts (`bridge_boot_mode_select`, deciding with `core/wifi_drive/drive_mode`): setup mode when a restart asked for it (RTC magic), otherwise the drive mode switch on GPIO32 (to ground, internal pull-up, read through ESP-IDF's GPIO driver about 1 ms after enabling the pull-up): open (or unfitted, or a broken wire) is Bluetooth drive, closed is WiFi drive. Setup mode and WiFi drive skip BTstack and Bluepad32 there.
- `scripts/build_identity.py`: a PlatformIO pre script that runs `cmake/build_identity.cmake` on every build, writing `build_identity_id.cpp` into the build directory (listed in `main/CMakeLists.txt`); PlatformIO's ESP-IDF builder never runs CMake custom targets. `setup()` in `bridge.cpp`, `setup_mode_start` and `wifi_drive_start` print `spooder bridge: build <id>` first, and `display::setup` queues `Build <id>` before `Boot` in the start-up log.
- `main/bridge.cpp`: Bluetooth drive: Bluepad32 callbacks (one controller slot) and `loop()`: gamepad → mapping → link, the screen, the GPIO0 hold into setup mode during the logo, and GPIO32 sampled for the switch notice (`SWITCH MOVED: RESTART`; it never changes the drive mode).
- `main/link`: `robot_link`, a FreeRTOS task above `loop()` that sends a command frame every 20 ms, samples the GPIO35 e-stop button and decodes telemetry and calibration reports; the robot's pose and diagnostics frames arrive too and are decoded, counted as accepted and, outside WiFi drive, ignored. In setup mode its commands come from the portal controller, and it sends calibration sets; in WiFi drive (`startHandheld`) from `core/wifi_drive/handheld_controller`, judged every period with its e-stop flag ORed with the GPIO35 toggle, and the robot's frames go raw into `relay_queue` for the UDP task, never waiting. (POSIX `link()` is visible on ESP-IDF, hence the name `robot_link`.)
- `main/display`: LovyanGFX ST7789 driver drawing the `status_screen` pages, at most every 250 ms, changed regions only, each through one reusable sprite; `main/screen_draw` draws each region in the Blackfyre dark palette onto any LovyanGFX surface (shared with `tools/bridge-screenshots`); the smooth fonts in `main/fonts/` come from `scripts/make_fonts.py` (`uv run`, by hand); in setup mode, the setup screen with the joining QR code.
- `main/wifi_drive`: the WiFi drive boot path (`wifi_drive_start`: frees the Bluetooth controller memory, then Arduino, the display, the link, the access point `spooder-drive-XXXX` with its own password in NVS `spooder`/`drive_pass`, channel 1, one station), the UDP task (priority 2, core 1: port 52040, at most 8 datagrams per 20 ms window, each stamped on receipt inside the link lock, the relay to the locked sender with `MSG_DONTWAIT`) and the WiFi drive task (priority 1: the screen, the logo hold into setup mode, the page button, the switch notice, the outcome counts on the console every 10 s when they change). Only `robot_link`'s handheld functions reach the controller and the relay, under the link's spinlock.
- `main/setup_mode`: the setup-mode boot path (RTC magic), the WiFi access point, the DNS and HTTP servers and the setup task. `main/portal_page.h` is the portal page, one hand-written HTML file.

## Rules

- **Warnings are errors in `main/`.** `main/CMakeLists.txt` compiles the `main` component, the bridge's sources and the shared `core/` files, with `-Wall -Wextra -Werror` (PRIVATE, so no other component), names again each warning ESP-IDF switches off (`-Wunused-parameter`, `-Wsign-compare`, …) and turns ESP-IDF's `-Wno-error=` exceptions into `-Werror=`. Fix a warning in the code, never with `-Wno-…`. A warning raised inside an SDK header (Arduino, Bluepad32, BTstack, LovyanGFX) is handled at the include, not project-wide: include LovyanGFX only through `main/lovyangfx_include.h`, which ignores `-Wunused-parameter` for its panel headers between `#pragma GCC diagnostic` push and pop; handle a new SDK header the same way.

- The bridge never runs WiFi and Bluetooth together: setup mode and WiFi drive are boot paths of their own and never start Bluetooth (no Bluepad32 or BTstack call on their paths); Bluetooth drive never starts WiFi. Leaving setup mode restarts into the drive mode the switch selects.
- `CONFIG_LWIP_UDP_RECVMBOX_SIZE=6` in `sdkconfig.defaults` must stay below the handheld's window budget (8), so the UDP backlog empties every window and no datagram is read more than 20 ms late.
- Values already in the generated `sdkconfig.ttgo-t-display` win over `sdkconfig.defaults`. After changing the defaults, delete that file once so they apply (the setup portal needs `CONFIG_ESP_WIFI_IRAM_OPT=n` to link).
- The partition table is `partitions.csv`, selected by `board_build.partitions` in `platformio.ini`: the pioarduino platform ignores the sdkconfig partition setting. The app is about 1.6 MB; the stock single-app tables (1 MB and 1.5 MB) do not fit it. The platform's own size check misses that (without an `ota_0` partition its limit is the whole 4 MB flash), so `scripts/check_image_size.py` checks the built image against the built table's factory partition, and that table against `partitions.csv`, on every build and before every upload; it prints the headroom. Its logic is tested by `mise run test-bridge-build`, which `mise run test` runs.
