# desktop/

The desktop calibrator, a Go module (`github.com/blackfyre/spooder/desktop`) with a Gio UI, kept apart so Gio and cgo never reach the firmware builds. Gates: `mise run desktop-test` (gofmt, go vet, staticcheck, go test), `mise run desktop-build` and `mise run e2e`.

**Dependencies.** Gio needs cgo and the Wayland, X11 and EGL development packages on Linux. On Fedora: `sudo dnf install wayland-devel libxkbcommon-devel libxkbcommon-x11-devel libX11-devel libXcursor-devel libXfixes-devel mesa-libEGL-devel vulkan-headers`. `desktop-build` and `desktop-test` run `desktop-deps` first, which prints the `dnf` line for whatever is missing. Opening the robot's port needs membership of the `dialout` group.

- `cmd/spooder-calibrator`: `main`, the wiring.
- `cmd/spooder-monitor` + `internal/console`: the text console behind `mise run monitor`. It uses the link read-only (no source, so no writer) and never sends a frame; only `--keys` writes, printable ASCII only. No Gio, and cgo only on macOS.
- `cmd/spooder-wifi-probe` + `internal/wifiprobe`: a stand-in for a WiFi handheld in the bridge's WiFi drive (no Gio, built without cgo to `build/desktop/spooder-wifi-probe`). After a 150 ms start-up wait it sends command frames at 50 Hz over UDP to the bridge (`--addr`, default `192.168.4.1:52040`) from a socket connected to it, with flags for one mode request, the e-stop flag and its clear, one fault clear, a pause to let the bridge's liveness lapse and a flood of copies of the latest frame; it prints a per-second summary of the robot frames relayed back, counting a datagram that is not exactly one valid robot frame, or that holds a command or calibration set frame, as an error. Its tests run it against a loopback UDP listener.
- `internal/protocol`: the link protocol in Go, byte for byte the C++ one, tested against `test/golden/protocol_v3.txt`; `FuzzDecoder` fuzzes the decoder (`fuzz_test.go`).
- `internal/link`: the serial port (`go.bug.st/serial`), the split of the stream into frames and debug text lines, the 20 ms writer (none for a nil source) and reconnecting by USB serial number; `FuzzSplitArbitrary` and `FuzzSplitInterleaved` fuzz the split (`fuzz_test.go`).
- `internal/session`: the single state owner: observe or control, the e-stop, mode and clear counters, driving (held keys and walking settings), telemetry, the latest pose, and the ten-minute history with its CSV export.
- `internal/legview`: the legs pane's geometry: forward kinematics (tested against `test/golden/leg_pose.txt`), leg mounting (tested against `test/golden/body_geometry.txt`), servo limits; and the whole robot in the body frame with the top, front, left and isometric projections (`views.go`) for the four-view window (`internal/ui/views.go`, its own Gio window); `gravity.go`, the estimated centre of gravity and support polygon that window draws, with a battery toggle (tested against `test/golden/centre_of_gravity.txt`).
- `internal/calib`: the joint table shown from reports, pending edits, one change in flight, resend and confirmation by request id.
- `internal/export`: `calibration_defaults.cpp` in the fixed format (tested against the fixture `test/golden/calibration_defaults.cpp`), the checkout check, the diff and the atomic write.
- `assets/`: the app icon, `icon.svg`, with its rendered PNGs and `icon.ico`.
- `internal/virtualrobot`: runs the virtual robot for tests; `e2e/`: end-to-end tests of the real link and session against it (skipped when it is not built).
- `internal/ui`: the Gio window in the Blackfyre look, with the charts tab (`charts*.go`: ten minutes of telemetry, diagnostics and pose on one time axis; series colours validated per mode); `internal/ui/fonts`: Archivo and JetBrains Mono for Gio, the files themselves (with their OFL licences) in the Gio-free `internal/ui/fonts/files`, which the handheld's drive screen and the bridge's `make_fonts.py` read too. `internal/appearance` and `internal/winreg` are copied from bopen (MIT, `LICENSE.bopen`).
- `handheld/`: the handheld controller, a NextUI tool pak (`Spooder.pak`) for a TrimUI Smart Pro that drives the robot through the bridge's WiFi drive. A **nested Go module** (`github.com/blackfyre/spooder/desktop/handheld`, `replace github.com/blackfyre/spooder/desktop => ../`), so it may import `desktop/internal/protocol` and `desktop/internal/session` while its cgo SDL2 and gabagool stay out of the calibrator's module and gates. Gates: `mise run handheld-test` (gofmt, go vet, staticcheck, go test), `mise run handheld-build` (amd64, `build/handheld/amd64/spooder-handheld`) and `mise run handheld-package` (the arm64 device build under rootless Podman, then `build/handheld/Spooder.pak.zip`); its e2e runs in `mise run e2e`. `handheld-test`, `handheld-build`, `handheld-build-device` (so `handheld-package`) and `e2e` depend on `handheld-fork`, which fetches gabagool v2.26.6 (checksum-checked), copies it to `build/handheld/gabagool` and applies `third_party/gabagool-power-hook.patch` (`Options.PowerButtonHook`); the nested `go.mod` replaces gabagool with that directory. SDL2 development packages: `mise run handheld-deps` (`scripts/check-deps.sh`) names the missing Fedora or Debian ones.
  - `cmd/spooder-handheld`: `main`, the only package importing gabagool or go-sdl2: the SDL controller table (`pad.go`, by the TrimUI's Nintendo labels: SDL's B is its A, SDL's X its Y; Back is Select, Guide is Menu), the drive screen (`screen.go`, 1280×720 in the Blackfyre dark look, and its driving-view page, `driveview.go`, a perspective chase camera behind the robot, 45° down, over the geometry of `desktop/internal/legview`, with a layout test and a drawing test that saves PNGs to `SPOODER_SCREENSHOTS`), the join message and the power-button hook.
  - `internal/padmap`: the line-for-line Go port of `core/gamepad_mapping` (tested against `test/golden/gamepad_mapping.txt`) and the handheld layer before it (Select as a modifier, Select + Start the e-stop toggle, Select + Y held 1 s the fault clear, Select + X the drive screen's page, the start in Sleep, combination buttons masked until released, a neutral pad during a leave).
  - `internal/udplink`: one connected UDP socket per run, the 150 ms start-up wait, command frames every 20 ms, the receiver that accepts only exactly one valid robot frame per datagram, the per-type display freshness and the link-quality counts.
  - `internal/app`: the run loop without SDL, the screen model, the leave state machine (Menu, a short or long Power press: Sleep requested, then two newer telemetry frames in a row reporting Sleep or output off, or 3 s, before exit, suspend or power-off), and `ParseFlags`/`Start` (`--device`, or `--addr` on desktop Linux).
  - `internal/wlan`: the 192.168.4.0/24 address check with one `udhcpc` renewal, the join message, the WiFi power-saving read, off and restore, and the signal level from `/proc/net/wireless`, all through an injectable runner.
  - `pak/launch.sh`: the pak's launch script (power saving saved and restored on every exit, the binary in its own process group), tested with stubs by `pak/launch_test.go`. `build/Containerfile` and `scripts/`: the device build (bullseye arm64 by digest, Go checked against `mise.toml`, `check-glibc.sh`: aarch64 and at most GLIBC_2.31) and the packaging. `e2e/`: the run loop and the bridge rules against the virtual robot's `--wifi-bridge` (skipped when it is not built).

## Rules

- The calibrator never opens a port by itself: it lists ports (the Servo 2040, USB ID 2e8a:000a, preselected; or the `--port` path) and connects on request. Its unit tests use in-memory ports or pseudo-terminals they create; the e2e tests use only the virtual robot's terminal.
- `internal/protocol` and `internal/legview` copy C++ behaviour; keep them in step through the golden files, never by editing a golden file to match.
- **Fuzz tests.** `go test` (so `desktop-test` and CI) replays each fuzz test's seed corpus and `testdata/fuzz/` without random inputs; `mise run fuzz` (`--time`, default `60s` per target) fuzzes them with random inputs. A new `Fuzz*` target is added to that task's list. A failing input Go saves under `testdata/fuzz/<Target>/` is committed with the fix as a regression case. The inputs that only add coverage stay in Go's build cache (`$(go env GOCACHE)/fuzz/`), as for any Go project; `go clean -fuzzcache` clears them.
- **The handheld** (`handheld/`): only `cmd/spooder-handheld` imports gabagool or go-sdl2; everything else is tested on the host without SDL. `internal/padmap` copies `core/gamepad_mapping` and is kept in step through `test/golden/gamepad_mapping.txt`, as `internal/protocol` is. The UDP socket is an outside input: a datagram is taken only as exactly one valid robot frame, and robot frames only update the screen and the leave confirmation, never what is sent. Anything the pak changes on the device (WiFi power saving) is restored however it exits, in Go and in `launch.sh`. `pak/launch.sh` and `scripts/*.sh` are POSIX `sh`, with no bashisms: `/bin/sh` is dash on Debian and Ubuntu (CI) and bash on Fedora, and `launch.sh` also runs under BusyBox ash on the device. Never `kill -SIG -- -PGID` (dash refuses `--`); `SPOODER_LAUNCH_SHELL` (such as `dash` or `busybox sh`) runs `pak/launch_test.go` under another shell. The gabagool pin is exact and the patch must apply (`handheld-fork` fails otherwise); a new gabagool version means re-reading its history and checking the patch.
